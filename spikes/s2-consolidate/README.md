# ADR 0001 S2 整理の計測

[Issue #18](https://github.com/cuzic/meetingram-core/issues/18) のマージしない spike。コアの合成会議 6 本と、架空の展示会の運営を話し合う 60 分・600 発話の `long` を使う。`long.gold.json` の `duplicate_issue_pairs` は、同じ問いを表す前半と後半の正解ノード ID の組。

長い会議の宿題は、記録係が今日の判断を進行表に転記すると引き受けた発話（行 ID 8、18、…、598）を根拠に 60 件付けた。各 action は直前の決定（行 ID 7、17、…、597）に `assigns` で結ぶ。次の行にある条件付きの確認の提案は、引き受けた作業や担当の依頼が発話にないため含めていない。

## fake で再現

```sh
cd spikes/s2-consolidate
cargo test --locked
cargo run --locked -- run --backend fake --out results/fake
cargo run --locked -- report --out results/fake
```

fake は最初の根拠を含む窓で正解のノードを返し、両端がそろった時点でエッジを返す。整理には空の操作列を返す。コアのプロンプト生成・応答解析・検証・評価を通し、7 本を流し切り、短い 6 本で両方式、長い 1 本で 2 段整理を完了する。長い会議の baseline は 1 回の入力上限（24,000 文字）を超え、試行は `baseline not applicable` と記録され、終了コードに影響しない。

## Claude が sandbox の外で実行

認証済みの `claude` が PATH にある環境で実行する。

```sh
cd spikes/s2-consolidate
./run-matrix.sh results/s2
```

スクリプトは 3 通りの呼び出し数の見積もりを最初に表示する。sonnet と haiku の各 7 本を 6 件／45 秒の窓で流し切り、両方式の整理を各 3 回実行する。続いて sonnet の短い 6 本を 12 件／90 秒の窓で流し切り、2 段整理を 1 回実行する。見積もりは発話窓と分割前の整理の回数を足した値。分割、プロンプトの上限で窓に入りきらなかった発話、再試行によって実際の回数は増える。`MAX_CALLS` で実行ごとの上限を変更できる（既定 700）。各実行の途中で上限や失敗に達した場合は、その時点までの結果を集計して次の実行へ進む。1 件でも実行または集計が失敗した場合は最後に非ゼロで終了する。

単独で実行する場合は新しい出力ディレクトリを指定する。

```sh
cargo run --locked -- estimate --backend claude-cli --model sonnet
cargo run --locked -- run --backend claude-cli --model sonnet --out results/sonnet
cargo run --locked -- report --out results/sonnet
```

## 出力と判定

- 各会議の `flush.json` を起点として読み戻し、毎回同じグラフから整理を始める。解析できた応答はコアで操作ごとに検証する。抽出で連続 3 回失敗した会議は整理を省く。整理で 1 回失敗した試行は打ち切り、流し切りのグラフへ戻す。
- `calls.jsonl` は呼び出しごとの経過時間、入出力の文字数、解析の可否、検証で落とした操作数、エラー種別、段 1 の添え書きの段階を記録する。CLI の作業場所は OS の一時ディレクトリに作り、終了時に削除する。グラフ JSON には合成会議の発話とノードの本文が含まれる。
- `RESULTS.md` は議題数、正解の議題数、細かな問いの数、再現率、適合率、エッジ F1、誤 merge 数、判定できない merge 数、正解の重複組の統合数、整理時間、タイムアウト数、呼び出し数、各段で省いたノード数、段 1 で添え書きを最も減らした段階、整理後に親を持つ対立した issue の数を試行ごとに表示する。対立の判定は、生きている position が 2 件以上、または関連する position が `objects_to` を受けていること。重複組は整理前の別々の予測 issue を根拠で正解に対応付け、整理後の統合先が一致した組を数える。
- 再現率は参考値の `node_recall` と条件 (3) に使う `content_recall` を並べて表示する。条件 (7) の `sub_question_only_agendas` も試行ごとに表示する。短い会議の親の付け直しと理由は [コアの正解 README](../../crates/discussion-graph/testdata/README.md) を参照。60 分の正解の issue は会場運営の方針を決める問いなので、すべて議題として扱う。
- ADR r15 のタスク 4b は sonnet の既定窓で判定する。短い 6 本では、2 段整理後の議題数の中央値を正解の議題数で割り、平均が 1.5 以下かつ各会議が 0.5〜2.5 かを見る。コアが誤りと判定した merge は、短い会議の中央値の合計が 2 件以下。判定できない merge は付録の本文の組を Claude が個別に確認し、誤りと判断した組を該当する試行の件数に加えて条件 (2) を確定する。各会議で内容再現率の中央値は baseline の中央値以上、細かな問いにだけ対応した正解の議題数の中央値は baseline の中央値以下を条件とする。baseline が入力上限で対象外の会議では、流し切り直後のグラフの値と比べる。長い会議は、正解の重複組の統合数の中央値が 3/3 なら合格。判定欄は各項目の値と合否、および会議別の議題の比を表示する。必要な試行が失敗または欠落した場合は判定を保留する。
- ADR r14 の記録では、段 1 が受理した `sub_issue_of` の追加と削除を試行ごとに数える。以前の試行データで段 1 の操作数を記録していない場合は表に `—` を表示する。`Parent samples` 付録は、各会議・各方式の完了した試行 1 について、段 1 が追加した親エッジをすべて `[stage 1]`、流し切りから整理後まで残った親エッジを最大 5 件 `[flush]` として、子と親の本文を表示する。
- `Changed matches` 付録は、会議・方式・試行ごとに、2 つの再現率で対応が変わった正解ノードの ID と本文、両指標の対応先の nid と本文を表示する。保存済みの出力ディレクトリを `report --out` に渡すと判定と付録を再生成できる。
