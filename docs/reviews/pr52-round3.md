## Findings

### M1（Major）: 「両立を妨げる制約は会議で述べられていない」という dd は、ADR に無い出力で、実際に大半の図の dd を空にする

- 根拠:
  - `cloud-system.txt:22` は、制約を述べた発話が無いときに「最もありそうな制約についての信念を inferred で書くか、『両立を妨げる制約は会議で述べられていない』とそのまま書き、打ち手は付けない」とする。
    この文は会議についての事実で、偽でありうる信念ではない。ADR 0006 §5 の「前提は … 偽でありうる信念として書く」から外れる。
    同じプロンプトの「前提にしないもの: … 争いのない事実」とも食い違う。ADR §5・§6 は、こうした決まり文句の前提を定めていない。
    描画では dd の位置に「〔推測〕両立を妨げる制約は会議で述べられていない」と出る。凡例は「推測: 会議では述べられていない。LLM が補った」なので、図の芯が推測の空欄になる。
  - このヘッドを測った spike r4（sonnet、22 候補 × 3 回）の出力を数えると、dd は全 66 回でちょうど 1 件ずつあり、そのうち **50 件がこの定型文**だった。
    会議で制約が述べられている候補にも出ている。`design/i-notice` と `e2e-design/i-notice` は 3 回ともで、u115「どちらも同じ欄になっている」がある。
    `m2/g3` は 3 回中 2 回で、u119「人が全然足りない」がある。プロンプトの「発話が制約を述べていれば、それを使い stated にする」が守られていない。
    言い回しも決まっていない（`design/i5` run2 は「…述べられていないから」）ので、アプリが見分けて「会議で確かめる問い」として出すこともできない。
  - これは仕様の判断（前提の種類を増やす、表示を変える）にあたる。AGENTS.md では、実装で決めずに ADR と owner に回すことになっている。
- 修正案: 定型の dd の選択肢を外し、「述べた発話があれば stated、無ければ最もありそうな制約を inferred の信念として書く」に戻す。
  r3 の埋め草（失敗 A）は、今の「埋め草は書かない」の一覧で抑える。
  定型の dd を残したいなら、先に ADR 0006 §5・§6 を改訂し（owner の判断）、次の 3 つを決めてから入れる: コアで文を定数にして検証で正規化する（打ち手は落とす）、
  アプリでの見せ方、spike で「制約を述べた発話がある候補では使わない」ことを確かめること。

### m8（Minor）: 良い例 2 つが、すぐ下で根拠なしでは禁じた「限られた…を取り合う」の型で、根拠のあるときの例だと書いていない

- 根拠: `cloud-system.txt:22` は「入力に根拠の無い『限られた…を取り合う』の型 … は作らない」と書く。良い例（`:31-32`）は
  「1 つしかないコンロの同じ口を使う」「任せられる家族が 1 人しかおらず」で、どちらもその型。発話で述べられた例なのか推測の例なのかが分からないので、
  モデルは「根拠が無ければこの型は使えない → 定型文」に流れやすい。M1 の 50/66 の一因と見られる。
